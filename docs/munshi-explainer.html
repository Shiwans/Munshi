Munshi मुंशी

A bookkeeper that lives in the chat. Small traders in Dadar market already write the day's business by hand in a diary or as notes to themselves. Munshi turns a typed line, a voice note, or a photo of the diary page into a proper khata: customers, udhaar, payments and the daily hisaab. The trader checks every entry before anything is saved.

Gemma reads. Code counts. The trader confirms.

Telegram delivers the messageadapter

telegram.js long-polls Telegram from the laptop, so there is no webhook and no tunnel. Photos are shrunk to 1280 px. Voice notes go through Whisper on the laptop first.

Easy messages never reach a modelcode

haan, nahi, 13 hatao, 4 rate 30, galti, X ka baaki, aaj ka hisaab are matched by rules in handler.js. Answer in under a second.

Gemma reads the restmodel

One call with function calling. It must answer through a tool: record_entries, get_khata, get_hisaab, statement, reply. It extracts qty, rate and any written total. It never adds or multiplies.

Code builds the cardcode

Names are matched to existing customers (alias, then spelling distance, then embeddings). ledger.js computes 72 × ₹28 in integer paise. If the diary's own total differs, the card asks which one is right.

The trader says haantrader

Only now are entries written and new customers created. Before that, the card lives in pending and can be corrected by row number.

Balances are always recomputedcode

Nothing like "balance" is stored. Every answer is summed from the entries, so totals can't drift.

Architecture

Small pieces, one brain, a swappable reader

Message text and photos go to the Gemini API for reading. The khata itself never leaves the laptop.

If the Gemini call fails, provider.js retries on the local Qwen automatically and the reply starts with "(offline munshi)". handler.js never imports an SDK, so adding a provider is one file.

Real diary, real check

The model reads the page. Code re-checks the diary's own arithmetic.

Tested on three scanned pages from a Dadar tomato trader: Devanagari names, rows written as qty⟩rate = total, payments in a middle column, supplier purchases on the right. Every row is recomputed in paise. Rounding to the rupee is accepted; real disagreements stop the save and ask.

Why it is not just a Gemma wrapper

The trust layer is ours

Money is integer paise

All totals, balances and the day's hisaab come from ledger.js, pure functions with unit tests. The model output has no total field it could fill.

No write without haan

Model output only becomes a pending card. New customers are tagged (naya customer) and created on confirm.

Entries are immutable

galti adds a reversing entry with reverses: <id>. Both stay visible, like a crossed line in a diary.

Tools only, no free numbers

Gemma is forced to answer through a function. The small-talk reply tool rejects any digits, so every number the trader sees came from code.

Learns each trader

Aliases from corrections, suppliers, the diary layout, and the last confirmed page as a worked example for the next photo.

Their language

Hinglish by default; Hindi, Marathi, Gujarati and English templates. The model cannot switch the language on its own.

Models (all open weights)

Four models, each with one job

gemma-4-26b-a4b-it

via the Gemini API

Reads Hinglish text and diary photos, function calling, minimal thinking for ~3 s replies. A full page takes ~25 s.

Qwen3.6-35B-A3B

local, LM Studio

Same tool interface. Fallback when the cloud fails, and the fully offline mode. Thinking off by prefilling an empty think block.

Whisper large-v3-turbo

local, mlx-whisper

Voice notes in Hinglish. ogg → 16 kHz wav → text in ~6 s on an M1 Pro. Audio never leaves the laptop.

nomic-embed-text-v1.5

local, LM Studio

Last step of name matching when spelling distance is not enough, cosine ≥ 0.85.

Three entry types cover any small trade: sale (cash or udhaar), payment (received), expense (own costs and supplier purchases). Balance = udhaar sales − payments, computed on every question. /export sends a CSV; /delete wipes the file after a yes.
